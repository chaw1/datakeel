## Task submission and pipelines

Task submission takes `dataset_id`, an `idempotency_key`, optional `version_id`, `pipeline`, `shards` and `queue`. Without `version_id`, tasks replay the imported snapshot. An explicit version consumes that immutable snapshot. A task's input list is frozen when submitted.

- **Sharding**: The default is one shard, so exact and approximate deduplication see the whole dataset. Explicit multi-shard execution suits independent transforms; deduplication stays local to each shard with no global reduction step.
- **Queues**: Queue names `cpu`, `io`, and `gpu` are supported; the built-in operator set provides CPU/IO operators.
- **DAG validation**: See [the contract guide](../contracts/README.md) for the typed DAG JSON format and generated operator manifest. Each operator emits an event even for an empty routed batch. Invalid DAGs are rejected before entering the queue.

## Evidence extraction and queries

Evidence extraction uses the `run_pipeline` action. Supply the preset returned by `datakeel.pipeline.evidence.evidence_pipeline()` as `pipeline`, with `dataset_id` and `shards=1`. The operator manifest lists the five evidence operators (`evidence.image_phash`, `evidence.caption_mentions`, `evidence.annotation_labels`, `evidence.label_gap`, and `evidence.near_duplicate`). Global near-duplicate extraction rejects multiple shards. Omitting `pipeline` retains the default pipeline.

Each extraction reports `inputs`, `skipped_cached`, `extracted` and `failed`, both overall and per operator. For the fresh default evidence corpus these are 5,000 inputs, 4,990 extracted and 10 image-decode failures; unchanged reruns hit cache on all 5,000 inputs and extract zero. The cache key includes actual input content, selector, extractor ID/version, schema version and both evidence-contract hashes. Changing only the caption extractor version re-extracts its 1,000 inputs, while other operators stay cached and old caption assertions are invalidated with an audit entry.

### ObjectSet 1.1 query example

`POST /api/evidence/query` accepts a flat ObjectSet 1.1 payload plus `cursor` and `page_size` (default 50, maximum 200). Results sort by asset ID; pass `next_cursor` for the next page. Replace `DATASET_ID` with the paired dataset's ID from `GET /api/datasets`:

```bash
DATASET_ID="replace-with-paired-dataset-id"
curl --fail http://127.0.0.1:8765/api/evidence/query \
  -H 'Content-Type: application/json' --data-binary @- <<EOF
{
  "schema_version": "1.1",
  "dataset_id": "${DATASET_ID}",
  "split": "val",
  "assertion_filters": [
    {"predicate": "mentions", "concept": "person", "value": "present"},
    {"predicate": "annotated_as", "concept": "person", "value": "present", "operator": "not_exists"}
  ],
  "has_near_duplicate_in": "train",
  "page_size": 20
}
EOF
```

`not_exists` means no matching annotation assertion, including `unknown` cases. To select confirmed gaps only, require `label_gap/person=present`. Legacy ObjectSet 1.0 manifests remain readable with their original serialization. Assertion filters are evaluated when preparing an action, and the resulting objects are frozen.

### Semantic lineage and projection rebuild

The lineage endpoint supports `include_semantic`, `asset_id`, `hops` (1–3) and `max_nodes` (1–1,000); semantic neighbors use deterministic BFS ordered by asset type and ID. `near_duplicate_of` projects to the `similar_to` link type. Extraction events reference content-addressed knowledge bundles; assertion bodies stay outside the event table.

Rebuild the assertion/cache projection and replay review audits with:

```bash
uv run datakeel rebuild-evidence
```

The command reports before/after canonical hashes including `PROJECTOR_VERSION`, and exits nonzero if they differ. After manually clearing a disposable projection, pass its saved hash with `--expected-hash` to verify against the original state.

## Semantic layer and metric definitions

The [semantic layer](../contracts/semantic-layer/metrics.yaml) separates `出货额` (ERP shipment prices, supply-chain owner), `销售额` (CRM booked invoices, finance owner), and `零售额` (completed orders at the paid price, retail owner). This abbreviated YAML illustrates the schema loaded when initializing an empty metric catalog:

```yaml
metrics:
  - id: retail_revenue
    name: 零售额
    english_name: Retail revenue
    synonyms: [终端零售额, 实付零售额, 营业额]
    description: Completed ecommerce orders at their paid amount, before later refunds.
    owner: 零售运营负责人
    version: 1
    measure:
      table: ecommerce/main/orders
      column: ecommerce/main/orders/paid_amount
      aggregation: sum
    filters:
      - column: ecommerce/main/orders/status
        op: eq
        value: completed
    time:
      column: ecommerce/main/orders/date
      granularity: day
    dimensions: [retail_region, retail_channel, retail_category]
    caveats:
      - Synthetic amounts in yuan; shipment, invoiced and retail amounts differ.
```

- `time` is required. Aggregations are `sum`, `count`, `count_distinct`, `avg`, `min`, `max`; filter `op` is `eq`, `ne`, `in`, `gte` or `lte`, with a list value only for `in`.
- Dimensions bind a registered `column` and may list static `values` and optional `value_synonyms`; terms use `means: {kind: metric|dimension|column, id: ...}`. Neither `grain` nor `values_source` is accepted.
- IDs use `source/schema/table[/column]`, with `main` for SQLite and percent-encoded separators/whitespace within segments. Missing references mark a metric `unresolved` with reasons and prevent query execution.
- Owner display metadata is declared in [`owners.yaml`](../contracts/semantic-layer/owners.yaml), keyed by the unchanged owner name.
- Controlled metric updates use `update_metric` / `rollback_metric` (and `update_term` / `rollback_term`). Changing `retail_revenue` from `paid_amount` to `list_amount` changes the demo Q4 question answer from `4,979,475` to `5,255,975`, recorded as a new version in `GET /api/catalog/metrics/retail_revenue/history`.
- Catalog imports use `import_catalog` / `restore_catalog`. Rebuild catalog projections and verify canonical hashes with `uv run datakeel rebuild-catalog`.

## Quality, governance templates and exports

- **Quality scoring**: Returns five dimension objects with weights 25 (completeness), 20 (consistency), 15 (uniqueness), 25 (annotation) and 15 (distribution). Unannotated data excludes the annotation dimension by default and renormalizes the remaining weights. For example, `{"min_size_bytes":999999}` lowers completeness and `{"thresholds":{"excellent":99}}` adjusts grade boundaries. Consistency groups by modality; distribution uses Shannon evenness.
- **Governance templates**: Templates accept JSON Schema or a `fields` mapping with required/enum/pattern constraints, and can be bound before completing metadata. Invalid saves are rejected atomically; accepted changes record before/after/source/reason and refresh 40/30/30 directory/naming/metadata compliance. Template references are local-only.
- **Standard exports**: `export --format openlineage` emits a JSON array where **each array element** is validated against the official RunEvent schema. Croissant 1.1 describes original source files and download URLs. Set `DATAKEEL_BASE_URL` for CLI exports served from another address; HTTP exports derive the address from the request.

## OpenTelemetry trace export

`datakeel export-traces [--conversation-id ID]` reads the existing trace store without migrating or writing it, then synchronously exports OTLP/HTTP protobuf spans carrying [OpenTelemetry GenAI client-inference conventions](https://github.com/open-telemetry/semantic-conventions-genai/blob/16f3130892e2e02fa3f0eef72c0e6b554ff08e5c/docs/gen-ai/client-inference.md) (currently **Development**) and OpenInference attributes. Prompts, completions, tool payloads, transcripts, model-route JSON and exporter credentials are not exported; span timestamps are approximate values reconstructed from settlement time and latency.

Only HTTP 200 responses with `rejected_spans=0` count as accepted, and there is no export cursor (repeating the command can create duplicate dashboard spans):

```bash
# Local OTLP collector
OTEL_EXPORTER_OTLP_TRACES_ENDPOINT=http://127.0.0.1:4318/v1/traces \
  uv run datakeel export-traces --conversation-id <id>

# Local Phoenix (OpenInference attributes are included)
OTEL_EXPORTER_OTLP_TRACES_ENDPOINT=http://127.0.0.1:6006/v1/traces \
  uv run datakeel export-traces --conversation-id <id>

# Langfuse: generic base endpoint and credentials supplied outside the repository
export OTEL_EXPORTER_OTLP_ENDPOINT=https://cloud.langfuse.com/api/public/otel
export OTEL_EXPORTER_OTLP_HEADERS='Authorization=Basic <base64-public-key-secret-key>,x-langfuse-ingestion-version=4'
uv run datakeel export-traces --conversation-id <id>
```
